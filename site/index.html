Capstone — funding & consent for AI-initiated payments

An agent that pays for you needs rails it can't talk its way out of.

A user loads gift cards into a dashboard. An agent goes to some place that wants money — a spec-native storefront, a hosted payment link, a subscription biller with no API at all — works out what's owed, decides how to pay from what it's been given, gets human approval when it should, pays, and handles failure sensibly.

The architecture's whole bet is one funding-and-consent core, many destination adapters — and an LLM that can only ever move money through rails it cannot exceed, never rails it talks its own way past.

This bet has since been tested in production, and it went the way this plan predicted.

OpenAI shipped close to the single-destination version of this idea — ACP-driven Instant Checkout inside ChatGPT — on 2025-09-29, live with Etsy and Shopify. It was pulled on 2026-03-24: only about 12 of Shopify's millions of merchants ever went live, and Walmart measured in-chat checkout converting roughly 3x worse than a normal click-through, despite higher-intent traffic. OpenAI's stated reason: it "did not offer the level of flexibility we aspire to provide."

That isn't proof this project's answer is right. It's evidence that the problem it bet on — a destination-agnostic core with an explicit consent layer, not a checkout button bolted onto a chat window — is a real, current failure mode, not a hypothetical invented for a capstone.

What the architecture answers, and what it doesn't yet

Revised 2026-08-23. The parts of "an agent that pays on your behalf" a user notices missing first — don't make me re-approve the same bill, don't let one high cap become unlimited spend — are built. What's left is harder and easier to defer: whether a destination can mechanically tell this agent apart from bot traffic, and real authentication in place of a fixture user.

Architecture, in three layers

Each layer maps to a published standard, checked against real reference implementations rather than invented from scratch.

Funding

What money, in what mix. UCP split-payments across a real instruments[] array — gift card drawn first, card rail for the remainder, byte-exact reversal on failure.

Consent

Did a human actually authorize this. AP2-named Intent/Checkout/Payment mandates, signed EdDSA-JWS, a policy gate before any draw, an append-only trail.

Arrival

Who is this agent, for whom. RFC 9421 request signing, as profiled by Visa TAP — the one layer still a stretch goal.

One planner, three destinations

The planner branches on capabilities, never on which destination it's talking to — enforced by a source lint (it never names a destination) and proven behaviourally by settling all three through it: a spec-native UCP storefront (machine-readable checkout), a hosted Stripe payment link (the real-rails leg — also where the physical Visa gift card's guarded live-decline path lives), and a simulated subscription biller with no API at all, which the agent has to scrape and knows to refuse rather than guess when the markup changes.

The brain is boxed by the rails, not trusted to be careful

A language model reads a plain instruction, drafts the spend cap and destination allowlist, and drives the deterministic orchestrator as tools — start_run, resume_run. It never constructs a charge, never holds a credential, never bypasses the policy gate. The core enforces the cap; the model proposes, it doesn't authorize. That ordering — safe substrate before autonomy — is the actual safety argument, not a disclaimer bolted on after.

Milestones

  1. M1
    Funding core.

    Gift-card ledger, append-only, both card families enrolled — closed-loop by code+PIN, open-loop via Stripe Elements so the PAN never reaches the server.

  2. M2
    Destinations + the money story.

    The PaymentDestination contract; one planner settling a UCP storefront and a Stripe payment link with no destination-specific branching.

  3. M3
    StreamCo + consent.

    The no-API biller; signed mandates; the policy gate and approval inbox; scoped payment tokens refusing replay, amount tampering, and reuse.

  4. M4
    The agent's brain.

    Instruct-to-pay: a provider-agnostic LLM driver, boxed by the same cap, mandates, and audit trail as the scripted runs.

  5. M4.5
    Standing authorization + cumulative cap.

    The two gaps a user notices first, closed without weakening the mandate model — both opt-in, both human-only.

  6. M5
    The real card — code path done.

    Enrolled-balance-as-hint in the planner; a guarded live path that can only ever produce a decline. The physical run itself is local-only, by design.

  7. M6
    Publish.

    This page, a deployed test-mode demo (Railway), and a recorded walkthrough.

What's honestly simplified

  • Mandates are plain signed JWS, not the spec's full SD-JWT-VC — correct names and binds, a simpler envelope.
  • Scoped payment tokens are this project's own, with the same binds as Stripe's issued Shared Payment Token — not enabled on this test account.
  • No real user authentication yet — the consent layer acts for a fixture user until a Supabase migration lands.
  • StreamCo is a faithful simulation of "a real biller with no agent-facing API" — real billers can't legally or technically be automated against, which is the point it's demonstrating.
